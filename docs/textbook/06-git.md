> **所要時間の目安**: 40分 ／ **前提**: 第5章まで

## 6-1 Git とは：作業の「セーブポイント」

Git（ギット）は、**ファイルの変更履歴を記録する仕組み** です。ゲームのセーブに例えると分かりやすくなります。

| ゲーム | Git | 意味 |
|---|---|---|
| セーブデータの置き場 | **リポジトリ** | Git で管理しているフォルダ |
| セーブする | **コミット** | 今の状態を、説明付きで記録する |
| セーブした地点に戻る | （コミットに戻す） | 失敗しても前の状態に戻れる |
| セーブデータをクラウドに預ける | **プッシュ** | 記録を GitHub などにアップロードする |

Claude Code は一度にたくさんのファイルを書き換えることがあります。**うまくいっている時点でセーブしておけば、失敗しても怖くありません**。これが、Claude Code を安心して使うための一番の土台です。

> 用語は[付録B 用語集](appendix-b-glossary.md)にもまとめています。

## 6-2 Claude に頼んで Git を使う

Git には本来たくさんのコマンドがありますが、**Claude に日本語で頼めば代わりにやってくれます**。覚えるのは「何を頼めばいいか」だけです。

### はじめに：Git で管理できるようにする

```text
このフォルダを Git で管理できるようにして
```

これで、このフォルダがリポジトリになります（最初の1回だけ）。

### よく使う頼み方

| やりたいこと | 頼み方の例 |
|---|---|
| セーブする | 「ここまでの変更を、分かりやすい説明付きでコミットして」 |
| 何が変わったか見る | 「前回のコミットから何が変わったか、分かりやすく説明して」 |
| 履歴を見る | 「最近のコミットを一覧にして、それぞれ何をしたか教えて」 |
| 前の状態に戻す | 「さっきのコミットの状態に戻して。戻す前に、消える変更がないか確認して」 |
| 試しに別の案を作る | 「今の状態はそのままにして、別案を試すためのブランチを作って」 |

**ブランチ** は「セーブデータの分岐」です。今の状態を残したまま、別の案を試せます。

> **注意**: 「前の状態に戻す」と、**まだコミットしていない変更は消えます**。不安なときは「戻す前に、消える変更がないか確認して」と必ず添えましょう。

### コミットのタイミング

さくらは、次のタイミングでコミットするようにしています。

- Claude に大きな作業を頼む **前**
- 「いい感じにできた」と思った **直後**
- その日の作業の **終わり**

迷ったら「こまめに」が正解です。コミットはいくらしても困りません。

## 6-3 `/rewind`（巻き戻し）と Git の違い

Claude Code には、会話やファイルを少し前の状態に戻す **巻き戻し機能** もあります。

- 入力欄が空の状態で `Esc` を2回押す、または `/rewind`（`/undo` でも可）
- 「ファイルも会話も戻す」「会話だけ戻す」「ファイルだけ戻す」などを選べる

便利ですが、**Git の代わりにはなりません**。

| | `/rewind` | Git |
|---|---|---|
| 戻せる範囲 | Claude が編集したファイルと会話 | フォルダ内の記録したファイル全部 |
| 戻せないもの | コマンド実行で変わったファイル、サブエージェントによる変更 | コミットしていない変更 |
| 記録の残り方 | その Claude Code の中だけ | ずっと残る。GitHub に預ければパソコンが壊れても安心 |
| 向いている場面 | 「今の指示はなかったことにしたい」 | 「この状態を確実に残したい」 |

**使い分け**: ちょっとしたやり直しは `/rewind`、大事な状態は Git でコミット。両方を組み合わせるのが安全です。

## 6-4 GitHub に預ける

**GitHub** は、Git のリポジトリをインターネット上に保存できるサービスです。パソコンが壊れても作業が残り、別のパソコンやクラウド（第14章）からも使えます。

### GitHub を使うときの3つのルール

1. **リポジトリは「非公開（Private）」にする**
   公開（Public）にすると、世界中の誰でも中身を見られます。仕事のファイルは必ず非公開にしましょう。
2. **秘密情報をコミットしない**
   API キー（サービスを使うための合言葉）やパスワードを書いたファイルを公開リポジトリにアップロードすると、**数分で見つけられて悪用される** ことがあります。
3. **`.env` などは `.gitignore` に入れる**
   `.gitignore` は「Git で記録しないファイル」の一覧です。秘密情報を書いたファイルはここに入れておきます。

Claude に頼むならこうです。

```text
.env ファイルを Git の記録対象から外すように .gitignore に追加して
```

```text
コミットする前に、API キーやパスワードなどの秘密情報が含まれていないか確認して
```

> **注意**: 一度 GitHub にアップロードした秘密情報は、あとから削除しても履歴に残ったり、すでにコピーされていたりします。もしアップロードしてしまったら、**すぐにそのキーやパスワードを無効にして作り直して** ください（各サービスの管理画面で行います）。秘密情報の扱いは第7章で詳しく説明します。

### push を禁止しておく

慣れないうちは、Claude が勝手にアップロードしないよう、第5章の deny ルールで push を禁止しておくと安心です。

```json
{
  "permissions": {
    "deny": ["Bash(git push *)"]
  }
}
```

アップロードしたいときは、自分で内容を確認してから行うか、一時的にこのルールを外します。

## 6-5 さくらの1日の流れ（例）

```text
（朝）
さくら: 昨日の作業の続きをしたい。最近のコミットを見て、どこまで終わっているか教えて
Claude: （履歴を見て）講座ページのデザインまで完了しています。料金表がまだです

さくら: 料金表を作る前に、今の状態をコミットして
Claude: （コミットする）

さくら: 料金表を作って。3コース、税込み表示で
Claude: （作成する）

（料金表のデザインがいまいち）
さくら: さっきのコミットの状態に戻して。戻す前に消える変更がないか確認して
Claude: 料金表の追加だけが消えます。戻してよいですか？
さくら: はい

（夕方、別案でうまくいった）
さくら: 今日の作業をコミットして
```

## やってみよう

### 演習1：最初のコミット

- **目的**: Git の管理を始めて、1回目のセーブをする
- **手順**:
  1. 練習用フォルダで Claude Code を起動する
  2. 「このフォルダを Git で管理できるようにして」と頼む
  3. 「メモ用の memo.md を作って、今日の日付と『Git の練習』と書いて」と頼む
  4. 「ここまでの変更をコミットして」と頼む
  5. 「最近のコミットを見せて」と頼む
- **期待する結果**: コミットの一覧に、今作ったコミットが表示される
- **うまくいかないとき**: Git がインストールされていないと言われたら、「Git をインストールする方法を教えて」と聞く。名前やメールアドレスの設定を求められたら、Claude に設定方法を聞く

### 演習2：わざと失敗して戻す

- **目的**: コミットに戻せることを体験する
- **手順**:
  1. 「memo.md の中身を全部消して『失敗』とだけ書いて」と頼む
  2. 「さっきのコミットの状態に戻して。戻す前に、消える変更がないか確認して」と頼む
- **期待する結果**: memo.md が元の内容に戻る
- **うまくいかないとき**: 演習1でコミットできていない可能性がある。「最近のコミットを見せて」で確認する

### 演習3：`/rewind` との違いを体験する

- **目的**: 巻き戻しの手軽さと限界を知る
- **手順**: memo.md に1行追加してもらったあと、入力欄が空の状態で `Esc` を2回押し、「ファイルも会話も戻す」を選ぶ
- **期待する結果**: 1行追加する前の状態に戻る
- **うまくいかないとき**: メニューが出ない場合は、入力欄に文字が残っていないか確認するか、`/rewind` と入力する

## まとめ

- Git は作業の **セーブポイント**。コミット＝セーブ、プッシュ＝クラウドに預ける
- コマンドを覚えなくても、**Claude に日本語で頼めば OK**
- 大きな作業の前と、うまくいった直後に **こまめにコミット**
- `/rewind` は手軽なやり直し。**大事な状態は Git で残す**
- GitHub は **非公開** で使い、**秘密情報はコミットしない**

## 確認テスト

**Q1.** 「コミット」と「プッシュ」の違いを説明してください。

<details><summary>答えを見る</summary>

コミットは、今の状態を自分のパソコンの中に記録すること（セーブ）。プッシュは、その記録を GitHub などにアップロードすること（クラウドに預ける）です。
</details>

**Q2.** 「さっきのコミットの状態に戻して」と頼むときに、添えたほうがよい一言は何ですか？

<details><summary>答えを見る</summary>

「戻す前に、消える変更がないか確認して」。戻すと、まだコミットしていない変更は消えてしまうからです。
</details>

**Q3.** `/rewind` で戻せない変更の例を1つ挙げてください。

<details><summary>答えを見る</summary>

コマンドの実行で変わったファイルや、サブエージェントによる変更です。だから大事な状態は Git でコミットしておきます。
</details>

**Q4.** API キーを書いたファイルを、うっかり公開リポジトリにプッシュしてしまいました。まず何をすべきですか？

<details><summary>答えを見る</summary>

すぐにそのサービスの管理画面で API キーを無効にして、新しいキーを作り直します。ファイルを削除するだけでは不十分です（履歴に残ったり、すでにコピーされたりしている可能性があるため）。
</details>
