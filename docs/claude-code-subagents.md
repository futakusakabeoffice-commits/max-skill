# Claude Code サブエージェント入門ガイド

> 対象: Claude Code を使い始めた人〜日常的に使っている人
> 情報の基準: 公式ドキュメント「Subagents」（https://code.claude.com/docs/en/sub-agents ）2026年11月時点
> Claude Code は更新が速いため、細かい仕様は公式ドキュメントで最新を確認してください。

---

## 1. サブエージェントとは

サブエージェントは、Claude Code（メインの会話）が仕事の一部を任せる **「専門の助手」** です。

- **自分専用のコンテキスト（記憶の作業台）** で動く
- **専用のシステムプロンプト**（役割・やり方の指示）を持つ
- **使える道具（ツール）を絞れる**
- **モデルや権限を個別に設定できる**

いちばん大事な性質は、**助手が途中で読んだファイルや試行錯誤はメインの会話に入らず、最終報告だけが戻ってくる** ことです。

```
あなた ──▶ メインの Claude
              │  「このバグの原因を調べて」
              ▼
         サブエージェント（別のコンテキスト）
           ・ファイルを50個読む
           ・テストを何度も実行
              │
              ▼  「原因は auth.ts 42行目。理由は〜」（要約だけ）
         メインの Claude（会話はスッキリしたまま）
```

### 使うメリット

| メリット | 内容 |
|---|---|
| コンテキストを節約 | 大量の検索結果やログをメインの会話に溜めない。長い作業でも会話が散らからない |
| 制約を強制できる | 「読むだけ」「編集はさせない」などをツール設定で確実に守らせる |
| 使い回せる | 一度作れば全プロジェクト・チーム全員で同じ助手を使える |
| 専門性が上がる | 役割を一つに絞った指示を書けるので、出力の質が安定する |
| コストを調整できる | 簡単な作業は Haiku など速くて安いモデルに任せられる |

> 注意: サブエージェントの利用も、メインの会話と同じ利用上限にカウントされます。「無料で並列に働く」わけではありません。

### 使うべき時・使わない方がいい時

| サブエージェント向き | メインの会話向き |
|---|---|
| 結果の要約だけ欲しい調査（大量のファイル検索、ログ解析） | 何度もやり取りしながら詰める作業 |
| ツールを制限して安全にやらせたい作業 | 前の話の流れを強く引き継ぐ作業 |
| それ単体で完結するタスク（レビュー、テスト実行など） | 1〜2行の小さな修正 |
| 互いに独立した作業を並行させたい時 | すぐ返事が欲しい作業（サブエージェントはゼロから文脈を読み直すぶん遅い） |

## 2. 最初から入っている（組み込み）サブエージェント

自分で作らなくても、Claude Code には次の助手が用意されています。Claude が必要に応じて自動で使います。

| 名前 | 役割 | ツール | モデル |
|---|---|---|---|
| **Explore** | コードベースの高速検索・調査。徹底度を `quick` / `medium` / `very thorough` から選ぶ | 読み取り専用（Write・Edit 不可） | 親（メイン）に合わせる |
| **Plan** | プランモード中の調査・計画づくり | 読み取り専用（Write・Edit 不可） | 親を継承 |
| **general-purpose** | 調べて、実際に手も動かす複数ステップの作業 | サブエージェントが使える全ツール | 親を継承（既定） |
| **claude** | 他に当てはまらない作業の受け皿 | サブエージェントが使える全ツール | モデルの決定順に従う |
| **statusline-setup** | `/statusline` の設定 | 設定用 | Sonnet |
| **claude-code-guide** | Claude Code の機能に関する質問に答える | 調査用 | Haiku |
| **web-fetch** | Webページを読む | Web取得 | Haiku（使えない場合は親のモデル） |

## 3. 自分でサブエージェントを作る

### 3-1. 一番かんたんな方法

- Claude Code で **`/agents`** と入力すると、サブエージェントの一覧表示・作成・編集ができる画面が開きます。
- または Claude に「○○を担当するサブエージェントを作って」と頼むだけでも作ってくれます。

### 3-2. ファイルで作る（基本の形）

サブエージェントの正体は **1つの Markdown ファイル** です。
上の `---` で囲んだ部分（YAML フロントマター）が設定、その下の本文が **システムプロンプト（助手への指示書）** になります。

```markdown
---
name: code-improver
description: ファイルを読んで、読みやすさ・性能・ベストプラクティスの観点から改善案を出す。コードを書いた後や修正した後に使う。
tools: Read, Grep, Glob
model: sonnet
---

あなたはコード改善の専門家です。
呼ばれたら次の手順で作業してください。

1. 対象ファイルを読み、目的を把握する
2. 読みやすさ・性能・保守性の問題を探す
3. 問題ごとに「現在のコード」「改善案」「理由」を示す
4. 重要度の高い順に並べて報告する

ファイルの編集はせず、提案だけを返してください。
```

保存したら、こう頼めば使われます。

```
code-improver エージェントを使って、このプロジェクトの改善点を挙げて
```

### 3-3. 置き場所と優先順位

同じ `name` のサブエージェントが複数あると、**上にあるものが優先** されます。

| 優先度 | 置き場所 | 使える範囲 |
|---|---|---|
| 1（最優先） | 管理者設定（Managed settings） | 組織全体 |
| 2 | `--agents` CLI フラグ | その起動中のセッションだけ |
| 3 | `.claude/agents/` | そのプロジェクト |
| 4 | `~/.claude/agents/` | 自分の全プロジェクト |
| 5 | プラグインの `agents/` ディレクトリ | プラグインを有効にした場所 |

ポイント:

- **チームで共有したいものは `.claude/agents/` に置いて Git にコミット**、自分専用なら `~/.claude/agents/` に置きます。
- フォルダはサブフォルダまで読まれます。サブエージェントの識別は **ファイル名やパスではなく `name` フィールド** で決まります。
- ファイルを追加・変更すると、基本的に再起動なしで反映されます。

### 3-4. CLI で一時的に定義する

ファイルを作らず、その起動の間だけ使うサブエージェントを JSON で渡せます（保存はされません）。

```bash
claude --agents '{
  "code-reviewer": {
    "description": "コードレビューの専門家。コードを変更した後に積極的に使う。",
    "prompt": "あなたは熟練のコードレビュアーです。品質・安全性・ベストプラクティスに注目してください。",
    "tools": ["Read", "Grep", "Glob", "Bash"],
    "model": "sonnet"
  }
}'
```

`prompt` が Markdown ファイルの本文（システムプロンプト）に当たります。

## 4. 設定項目（フロントマター）リファレンス

**必須は `name` と `description` の2つだけ** です。複数単語の項目名はキャメルケース（例: `disallowedTools`）で書きます。知らない項目名は **エラーにならず無視される** ので、綴り間違いに注意してください。

### よく使う項目

| 項目 | 内容 | 例 |
|---|---|---|
| `name` | 識別名（必須）。重複不可。`:` は使えない | `code-reviewer` |
| `description` | **いつこの助手に任せるべきか**（必須）。Claude はこれを読んで自動で任せるかを決める | `コード変更後にレビューする。積極的に使う。` |
| `tools` | 使ってよいツールの許可リスト。**省略すると使えるツールをすべて継承** | `Read, Grep, Glob` |
| `disallowedTools` | 使わせないツールの禁止リスト。`tools` と両方にあれば禁止が優先 | `Write, Edit` |
| `model` | 使うモデル。`sonnet` / `opus` / `haiku` / `fable` / 完全なモデルID / `inherit`（親と同じ） | `haiku` |

### 必要に応じて使う項目

| 項目 | 内容 |
|---|---|
| `permissionMode` | 権限モード。`default` / `acceptEdits` / `auto` / `dontAsk` / `bypassPermissions` / `plan` など |
| `maxTurns` | 最大ターン数。超えると途中結果として返り、後で再開できる |
| `skills` | 起動時に読み込ませるスキル（中身がまるごと渡される） |
| `mcpServers` | このサブエージェントだけが使う MCP サーバー（名前で参照、または中に直接定義） |
| `hooks` | このサブエージェントが動いている間だけ有効なフック |
| `memory` | 会話をまたいで覚えるメモリ。`user` / `project` / `local`（公式の推奨既定は `project`） |
| `background` | `true` にすると常にバックグラウンドで動かす |
| `isolation` | `worktree` にすると一時的な git worktree（作業用の別コピー）で動く。メインの作業ファイルを汚さない |
| `effort` | 思考の深さ。`low` / `medium` / `high` / `xhigh` / `max` |
| `omitClaudeMd` | `true` で CLAUDE.md を読み込ませない |
| `color` | 画面上の表示色。`red` / `blue` / `green` / `yellow` / `purple` / `orange` / `pink` / `cyan` |
| `initialPrompt` | `--agent` でメインとして起動したときに自動で送る最初の指示 |

> プラグインに入っているサブエージェントでは、安全のため `permissionMode`・`hooks`・`mcpServers` は無視されます。

### ツールの書き方の例

```yaml
tools: Read, Grep, Glob, Bash     # この4つだけ許可
disallowedTools: Write, Edit      # 書き込み系だけ禁止（他は継承）
tools: mcp__github__*             # GitHub MCP サーバーのツールをすべて許可
disallowedTools: mcp__github      # GitHub MCP サーバーのツールをすべて禁止
```

### モデルが決まる順番

上から順に見て、最初に見つかったものが使われます。

1. Claude が呼び出し時に指定したモデル
2. 定義ファイルの `model`（`inherit` を含む）
3. 環境変数 `CLAUDE_CODE_SUBAGENT_MODEL`
4. メインの会話のモデル（入れ子の場合は呼び出し元サブエージェントのモデル）

## 5. サブエージェントの呼び出し方

| 方法 | やり方 | 向いている場面 |
|---|---|---|
| **自動で任せる** | 何もしない。Claude が `description` を見て判断 | 普段使い |
| **言葉で指名** | 「test-runner サブエージェントを使って失敗しているテストを直して」 | 確実にその助手を使わせたい |
| **@メンション** | `@` を入力して選ぶ、または `@agent-<名前>` と書く（プラグインは `@agent-<プラグイン名>:<名前>`） | 素早く指名したい |
| **セッション全体をその助手に** | `claude --agent code-reviewer`、または `.claude/settings.json` に `"agent": "code-reviewer"` | 会話全体をその役割で進めたい |

> `--agent` でセッション全体を任せると、そのサブエージェントのプロンプトが Claude Code の標準システムプロンプトの **代わり** になります。

### 自動で任せてもらうコツ

自動で使われるかどうかは **`description` の書き方でほぼ決まります**。

- 悪い例: `コードレビュー`
- 良い例: `コードの品質・安全性・保守性をレビューする専門家。コードを書いたり変更したりした直後に積極的に（proactively）使う。`

「何をするか」に加えて **「どんな時に使うか」** を書き、`use proactively`（積極的に使う）という表現を入れると、任されやすくなります。

## 6. 動き方の詳細

### フォアグラウンドとバックグラウンド

| | フォアグラウンド | バックグラウンド |
|---|---|---|
| メインの会話 | 終わるまで待つ | 並行して会話を続けられる |
| 権限の確認 | そのまま表示される | メイン画面に「どのサブエージェントからか」付きで表示される |

- 実行中のタスクは **Ctrl+B** でバックグラウンドに回せます。
- 確認画面で **Esc** を押すと、そのツール実行だけを拒否し、サブエージェント自体は止まりません。

### サブエージェントが最初に知っていること

通常のサブエージェントは **メインの会話の履歴を見られません**。起動時に渡されるのは次のものだけです。

- 自分のシステムプロンプト
- Claude からの依頼文
- CLAUDE.md（`omitClaudeMd: true` なら除く）
- git の状態（Explore と Plan を除く）
- 事前に読み込むよう指定したスキル

→ **依頼文に必要な情報（目的・対象ファイル・完了条件）を書き切ることが重要** です。

### フォーク（会話を引き継ぐ分身）

通常のサブエージェントとは別に、**それまでの会話をまるごと引き継いだ分身（フォーク）** を作る仕組みもあります。

- `/subtask <やること>` で自分でフォークを始められます（例: `/subtask ここまでのパーサー変更の単体テストを書いて`）
- フォークは親と同じ文脈を持つので、説明し直す必要がありません
- フォークからさらにフォークは作れません

### 続きを頼む（再開）

- 呼び出すたびに、基本は **新しいサブエージェント** が作られます。
- 終わったサブエージェントには ID が付き、Claude はその ID を使って **続きの仕事を頼めます**（それまでの記憶を保ったまま）。
- 記録は `~/.claude/projects/{プロジェクト}/{セッションID}/subagents/` に保存され、既定では30日後に削除されます。

### サブエージェントがサブエージェントを呼ぶ（入れ子）

- 既定で、メインの下 **3階層まで** 入れ子にできます。
- 呼ばせたくない場合は、`tools` に `Agent` を入れない、または `disallowedTools` に `Agent` を入れます。
- 同時に動かせるサブエージェントは既定で20個までです。

## 7. すぐ使える実例

### 例1: コードレビュー担当（読むだけ）

`.claude/agents/code-reviewer.md`

```markdown
---
name: code-reviewer
description: コードの品質・安全性・保守性をレビューする専門家。コードを書いたり変更したりした直後に積極的に使う。
tools: Read, Grep, Glob, Bash
model: inherit
---

あなたは経験豊富なシニアエンジニアとしてコードレビューを行います。

呼ばれたら:
1. `git diff` を実行して最近の変更を確認する
2. 変更されたファイルに集中してレビューする

チェック項目:
- 読みやすさ（名前の付け方、重複がないか）
- エラー処理
- 秘密情報（APIキーなど）が含まれていないか
- 入力チェック
- テストがあるか

結果は重要度順に、次の3段階で報告する:
- 🔴 必ず直す（重大）
- 🟡 直した方がよい（警告）
- 🟢 検討してほしい（提案）

それぞれ、具体的な直し方の例を付けること。
```

> `Write`・`Edit` を外していても `Bash` があればファイルは変更できてしまいます。完全に読み取り専用にしたいなら `Bash` も外すか、下の例4のようにフックで制限します。

### 例2: デバッグ担当（直すところまで）

```markdown
---
name: debugger
description: エラー・テスト失敗・想定外の動作の原因を調べて直す専門家。問題が起きたら積極的に使う。
tools: Read, Edit, Bash, Grep, Glob
---

あなたは根本原因の分析が得意なデバッグの専門家です。

1. エラーメッセージとスタックトレースを記録する
2. 再現手順を特定する
3. 失敗している場所を絞り込む
4. 最小限の修正を入れる
5. 直ったことを確認する

報告には、根本原因・その根拠・修正内容・確認方法・再発防止の提案を含めること。
症状だけを隠す修正はしない。
```

### 例3: 安くて速い調査担当

```markdown
---
name: quick-researcher
description: 「どこに書いてある？」「何ファイルある？」のような単純な調べものを担当する。結果は短く要約して返す。
tools: Read, Grep, Glob
model: haiku
color: cyan
---

指定された内容をコードベースから探し、結論だけを箇条書きで返してください。
ファイルパスと行番号を必ず添えること。推測は「推測」と明記すること。
```

### 例4: フックで SQL を読み取り専用に制限

`tools` では「Bash は使ってよいが、書き込み系の SQL は禁止」のような細かい制限はできません。そういう時はフックを使います。

```markdown
---
name: db-reader
description: データベースに読み取り専用のクエリを実行して分析する。
tools: Bash
hooks:
  PreToolUse:
    - matcher: "Bash"
      hooks:
        - type: command
          command: "./scripts/validate-readonly-query.sh"
---

あなたはデータ分析担当です。SELECT 文だけを使ってデータを調べ、結果を分かりやすくまとめてください。
```

`scripts/validate-readonly-query.sh`（実行権限 `chmod +x` が必要）

```bash
#!/bin/bash
# ツールの入力（JSON）は標準入力で渡される
COMMAND=$(jq -r '.tool_input.command')

# 書き込み系の SQL が含まれていたらブロック
if echo "$COMMAND" | grep -iE '\b(INSERT|UPDATE|DELETE|DROP|CREATE|ALTER|TRUNCATE)\b' > /dev/null; then
  echo "書き込み系の操作はできません。SELECT を使ってください。" >&2
  exit 2   # 終了コード 2 = ツール実行をブロック
fi
exit 0
```

## 8. 上手に使うためのベストプラクティス

1. **1つの助手に1つの役割**
   「レビューもテストもドキュメントも」ではなく、役割ごとに分けます。
2. **`description` は「いつ使うか」まで具体的に**
   他の助手と役割がかぶらないように書きます。全サブエージェントの説明の合計が大きすぎる（約15,000トークン超）と警告が出ます。
3. **ツールは必要最小限に**
   読むだけの仕事には `Read, Grep, Glob` だけ。安全で、動きも予想しやすくなります。
4. **作ったらチームで共有**
   プロジェクト用の助手は `.claude/agents/` に置いて Git で管理します。
5. **依頼文に情報を書き切る**
   サブエージェントはメインの会話を見ていません。目的・対象・完了条件・報告の形式を伝えます。CLAUDE.md のルールを特に守らせたい時は、依頼文でも念押しします。
6. **報告は短く要約させる**
   サブエージェントの報告が長いと、結局メインの会話のコンテキストを消費します。「結論と根拠を10行以内で」などと指示しておきます。
7. **細かい制限はフックで**
   `tools` で表現できないルール（特定コマンドの禁止など）は `PreToolUse` フックで実現します。

## 9. よくあるつまずき

| 症状 | 原因と対策 |
|---|---|
| 作ったのに自動で使われない | `description` があいまい。「いつ使うか」と `use proactively` を書く。または名前で指名する |
| 設定が効いていない | 項目名の綴りミス（未知の項目は無視される）。`disallowed_tools` ではなく `disallowedTools` |
| 同じ名前の助手が別の動きをする | 優先順位の高い場所に同名の定義がある。`/agents` で確認する |
| サブエージェントが前の話を知らない | 仕様通り。依頼文に必要な文脈を書く（会話を引き継ぎたいならフォークを使う） |
| メインの会話がすぐいっぱいになる | サブエージェントの報告が長すぎる。要約の長さを指定する |
| 「読むだけ」のはずがファイルが変わった | `Bash` が許可されている。外すかフックで制限する |

---

## 10. まとめ

- サブエージェントは **専用のコンテキスト・指示・ツールを持つ専門の助手**。結果の要約だけが戻るので、メインの会話がきれいに保てる。
- 作り方は **Markdown ファイル1つ**。必須は `name` と `description` だけ。
- 置き場所は、チーム共有なら `.claude/agents/`、自分用なら `~/.claude/agents/`。
- 自動で使われるかは **`description` 次第**。ツールは最小限に、役割は1つに。
- 迷ったらまず `/agents` を開いて、組み込みの助手と自分の助手を確認しよう。
